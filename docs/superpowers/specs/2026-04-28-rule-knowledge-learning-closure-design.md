# 转规则与转知识学习闭环设计

## 背景

筛稿、编辑和校对过程中会产生大量可沉淀经验：AI 命中的规则、AI 未覆盖但人工确认的差异、人工补充的处理意见、以及最终稿中确认有效的改动。现有系统已经有规则中心、知识库、知识审核、学习候选、review item、learning writeback、规则激活指标和知识命中日志等基础，但用户感知上仍容易出现两个问题：

- “转规则”或“转知识”像是按钮和状态，不像是真正进入后续工作台。
- 回流后的候选没有复用规则中心和知识库的完整录入原则，容易漏掉适用范围、证据、AI 语义解析和发布治理信息。

本设计目标是建立真实、可追溯、可审核、可发布的学习闭环：处理稿件时勾选转规则或转知识后，系统把候选直接送入已有的规则中心或知识库工作台，由人工完整编辑和审核，发布后进入运行时使用，并在对应总览表展示学习效果指标。

## 目标

- 筛稿、编辑、校对完成后，所有勾选“转规则”的项目都能形成可追溯的规则候选，并进入规则中心完整编辑与发布链路。
- 所有勾选“转知识”的项目都能形成可追溯的知识候选，并进入知识库完整编辑、知识审核与生效链路。
- 不新增独立的“上层回流中心”。路由逻辑在后端和入口链接中完成，真实处理仍发生在规则中心和知识库。
- 转规则和转知识必须复用现有新建规则、新建知识的字段提取原则、AI 语义解析、证据保留和审核发布规则。
- 规则中心总览和知识库总览以多维表格列展示学习效果，指标来自日志和派生统计，不污染核心资产表。
- AI 的角色是提出候选、预填字段、生成语义解析和辅助归类；人工确认和受控发布仍是强制门槛。

## 非目标

- 不让 AI 自动发布正式规则或正式知识。
- 不新增全局回流队列或独立回流工作台。
- 不把命中次数、误报率、引用次数等运行指标直接写入规则或知识核心定义表。
- 不用简化表单替代规则中心、知识库已有的完整编辑器。
- 不把 Harness 作为日常查看学习效果的主入口。
- 不在本阶段重写筛稿、编辑、校对的完整工作台。

## 核心原则

### 候选只负责预填，资产仍由专业工作台创建

转规则候选不等于规则。它只携带来源、证据、建议字段和 AI 解析结果，打开规则中心的新建规则或规则包编辑器后，由人工修改、校验、保存为规则草稿并发布。

转知识候选不等于知识。它只携带来源、证据、建议字段和 AI 语义层，打开知识库的新建知识编辑器后，由人工修改、提交知识审核并批准为正式知识。

### 不新增上层中心

用户不需要看一个总的学习队列，也不需要人工判断该去哪里。系统已经知道用户点的是转规则还是转知识，所以应直接进入对应工作台：

- `转规则` 打开规则中心候选预填入口。
- `转知识` 打开知识库候选预填入口或知识审核准备页。

这样能减少导航、权限、状态同步和数据重复展示的复杂度。

### 证据链必须贯穿

每个候选必须保留：

- 来源模块：screening、editing、proofreading。
- 来源稿件 ID。
- 来源执行快照 ID。
- 来源最终稿或人工确认资产 ID。
- 原文片段和处理后片段。
- 人工确认动作和备注。
- AI 建议或人工补充原因。
- 相关规则、相关知识、质量包和命中日志。

正式规则或正式知识发布后，仍能追溯到原始候选和来源稿件。

### 指标是派生读模型

总览表可以显示效果列，但这些列必须来自运行日志、指标表、物化视图或查询聚合。核心规则表和知识资产表只保存定义、版本、状态和治理信息，不保存不断变化的运行统计。

## 用户流程

### 处理稿件阶段

筛稿、编辑、校对的确认界面保留当前处理动作，并明确增加两个学习动作：

- `转规则`：适合稳定、可执行、可复用的操作规范。
- `转知识`：适合背景知识、写作说明、期刊要求解释、医学常识、格式说明、人工处理经验。

用户可在 AI 建议项、人工补充项、最终稿差异项、残差问题项中勾选这两个动作。发布最终稿或完成处理时，系统生成对应 learning candidate，并保存候选来源链路。

### 转规则流程

1. 用户在处理稿件时选择 `转规则`。
2. 系统创建 `rule_candidate`，状态为 `pending_review`，并附加治理来源。
3. 规则中心展示可处理的规则候选入口。
4. 用户打开候选后进入规则中心已有的新建规则或规则包编辑器。
5. 编辑器使用候选内容预填完整字段。
6. AI 解析规则语义，补全或提示以下字段：
   - 规则对象。
   - 适用模块。
   - 稿件类型。
   - 章节范围。
   - 触发条件。
   - 执行动作。
   - 正例和反例。
   - 不适用边界。
   - 风险姿态。
   - 人工复核条件。
   - 相关证据。
7. 人工修改并保存为规则草稿。
8. 规则中心执行现有预览、校验、冲突检查、发布流程。
9. 发布后规则进入运行时解析和执行。
10. 规则中心总览表显示该规则的效果列。

### 转知识流程

1. 用户在处理稿件时选择 `转知识`。
2. 系统创建 `knowledge_candidate`，状态为 `pending_review`，并附加治理来源。
3. 用户打开知识库候选入口，进入知识库已有的新建知识编辑器。
4. 编辑器使用候选内容预填完整字段。
5. AI 语义解析补全或提示以下字段：
   - 标题。
   - 摘要。
   - 正文。
   - 知识类型。
   - 适用模块。
   - 稿件类型。
   - 章节范围。
   - 风险标签。
   - 学科标签。
   - 证据等级。
   - 来源类型和来源链接。
   - 别名。
   - 检索词和检索片段。
   - 绑定的模板、规则或知识条目。
6. 人工修改并保存知识草稿。
7. 用户提交知识审核。
8. 知识审核页完成批准或驳回。
9. 批准后成为当前 approved revision，进入知识检索和运行时上下文。
10. 知识库总览表显示该知识的效果列。

## 工作台设计

### 规则中心

规则中心不需要新增“回流中心”页面，只需要把规则候选作为新建规则的一个来源。

推荐入口：

- 规则中心总览表增加筛选项：`来源 = 回流候选`。
- 规则中心总览表增加状态：`待转草稿`、`草稿待发布`、`已发布`、`已驳回`。
- 规则中心新建按钮旁增加轻量入口：`从回流候选创建`。

候选进入编辑器后，不使用简化表单。它必须进入当前规则中心完整编辑体验，并带入候选来源证据。

### 知识库

知识库同样不新增独立回流中心，只把知识候选作为新建知识的一个来源。

推荐入口：

- 知识库总览表增加筛选项：`来源 = 回流候选`。
- 知识库总览表增加状态：`待转草稿`、`草稿待审核`、`审核通过`、`已驳回`。
- 知识库新建按钮旁增加轻量入口：`从回流候选创建`。
- 知识审核页继续处理已经提交审核的知识 revision。

候选进入知识编辑器后，必须复用知识库富文本、内容块、表格、图片、语义层、绑定关系和重复检测能力。

## 数据模型建议

### Learning candidate

继续使用现有 learning candidate 作为候选主记录。需要确保 `rule_candidate` 和 `knowledge_candidate` 都具备完整来源字段：

- `type`：`rule_candidate` 或 `knowledge_candidate`。
- `status`：draft、pending_review、approved、rejected。
- `module`。
- `manuscript_type`。
- `manuscript_id`。
- `proposal_text`。
- `candidate_payload`。
- `governed_provenance_kind`。
- `snapshot_asset_id` 或来源快照字段。
- `source_learning_candidate_id` 用于写回后追溯。

### Candidate payload

`candidate_payload` 应承担跨工作台预填数据，不应成为正式资产定义。建议结构分区：

- `source_evidence`：稿件、快照、资产、片段、人工备注。
- `diff_payload`：处理前、处理后、操作类型。
- `ai_semantic_suggestion`：AI 语义解析结果。
- `rule_prefill`：规则编辑器预填字段。
- `knowledge_prefill`：知识编辑器预填字段。
- `quality_context`：质量包、命中日志、相关规则或知识。

### Writeback

继续使用 learning writeback 记录候选写回结果。

- `editorial_rule_draft` 写回生成规则草稿或规则包草稿。
- `knowledge_item` 写回生成知识草稿或知识 revision。
- 写回状态只代表草稿已创建，不代表正式发布。

### 效果指标

不在核心资产表中写入运行指标。推荐使用独立读模型：

- 规则：继续利用或扩展 `editorial_rule_activation_metrics`。
- 知识：基于 `knowledge_hit_logs`、retrieval snapshots、execution snapshots 生成 `knowledge_usage_metrics` 或查询聚合。

规则指标建议字段：

- `rule_id`。
- `rule_set_id`。
- `metric_window`：all_time、last_30_days、last_7_days。
- `governed_hit_count`。
- `auto_apply_count`。
- `manual_review_count`。
- `false_positive_count`。
- `routed_rule_candidate_count`。
- `writeback_applied_count`。
- `last_hit_at`。

知识指标建议字段：

- `knowledge_item_id`。
- `revision_id`。
- `metric_window`：all_time、last_30_days、last_7_days。
- `retrieval_hit_count`。
- `runtime_reference_count`。
- `accepted_usage_count`。
- `manual_confirmed_effective_count`。
- `revision_count`。
- `last_used_at`。

默认总览表显示 `last_30_days` 和当前生效版本。详情页可以展示累计和历史版本趋势。

## API 设计

### 规则候选到规则草稿

需要一个明确的前端入口和后端能力组合：

- 前端读取 `rule_candidate`。
- 前端把候选映射为规则编辑器 draft state。
- 用户保存后调用现有规则中心保存草稿接口。
- 后端通过 learning writeback 标记候选已经写回。

推荐避免新增大而全接口。优先复用：

- learning candidate 查询。
- learning governance writeback 创建和应用。
- 规则中心 create rule set、create rule、preview、publish。

### 知识候选到知识草稿

需要补齐当前界面缺口：

- 前端读取 `knowledge_candidate`。
- 前端把候选映射为知识库 create draft state。
- 用户保存后调用知识库 create library draft 或 create knowledge draft。
- 后端通过 learning writeback 标记候选已经写回。
- 用户提交知识审核后继续走现有知识审核接口。

优先复用：

- learning candidate 查询。
- learning governance writeback 创建和应用。
- 知识库 draft、revision、semantic layer、submit、approve、reject。

## AI 语义解析要求

转规则和转知识都必须包含 AI 语义解析，但解析结果不能直接发布。

规则解析输出：

- 规则含义摘要。
- 命中对象。
- 命中位置。
- 适用范围。
- 触发条件。
- 执行动作。
- 正反例。
- 不适用边界。
- 人工复核条件。
- 字段置信度。
- 不确定点。

知识解析输出：

- 标题建议。
- 摘要建议。
- 正文结构。
- 检索词。
- 检索片段。
- 适用范围。
- 学科标签。
- 风险标签。
- 证据等级建议。
- 绑定关系建议。
- 字段置信度。
- 不确定点。

发布前必须有人工确认或人工覆盖记录。

## UI 细节

### 候选预填提示

规则中心和知识库编辑器顶部显示候选来源条：

- 来源模块。
- 来源稿件。
- 来源快照。
- 来源资产。
- 原文片段。
- 处理后片段。
- 人工备注。

该条不应遮挡主要编辑区域，可以折叠。

### 总览表效果列

规则中心总览建议列：

- 状态。
- 来源。
- 适用范围。
- 近 30 天命中。
- 自动应用。
- 人工复核。
- 误报率。
- 最后命中。

知识库总览建议列：

- 状态。
- 来源。
- 适用范围。
- 近 30 天引用。
- 检索命中。
- 被采用。
- 修订次数。
- 最后使用。

效果列需要支持排序和筛选，但默认不参与核心发布判断。

### 指标解释

每个效果列提供简短说明，避免操作员误读：

- `近 30 天命中` 表示当前生效版本在最近 30 天的运行命中。
- `自动应用` 表示无需人工确认即被执行的次数。
- `人工复核` 表示命中后进入人工确认的次数。
- `检索命中` 表示知识被检索召回的次数，不等同于最终采用。
- `被采用` 表示知识进入执行上下文并被后续处理引用。

## 权限和安全

- 普通处理员可以在稿件处理阶段勾选转规则或转知识。
- 规则草稿保存和发布沿用规则中心权限。
- 知识草稿保存和知识审核沿用知识库和知识审核权限。
- AI 语义解析结果必须标记为建议，不得伪装为人工结论。
- 发布前必须保留人工审核记录。
- 指标列只读，不能反向修改核心资产。

## 错误处理

- 候选创建失败不能阻塞最终稿发布，但必须提示“学习回流失败，可稍后重试”。
- 写回草稿失败不能改变候选审核状态，应保留重试入口。
- AI 解析失败时允许人工继续编辑，但提交审核或发布时必须显示解析缺口。
- 指标读取失败时，总览表显示 `暂无数据`，不能阻塞规则或知识管理。
- 来源资产不存在时，候选仍可编辑，但必须显示证据链不完整风险。

## 测试策略

### 后端

- 校对最终稿发布后，转规则生成 `rule_candidate`，转知识生成 `knowledge_candidate`。
- 编辑和筛稿治理命中可以路由到对应候选。
- `rule_candidate` 审核通过后能写回规则草稿。
- `knowledge_candidate` 审核通过后能写回知识草稿。
- 写回只创建草稿，不自动发布。
- 知识草稿提交审核并批准后能成为 approved revision。
- 规则发布后刷新运行时规则投影。
- 指标聚合不写入核心资产表。

### 前端

- 转规则候选打开规则中心完整编辑器并预填字段。
- 转知识候选打开知识库完整编辑器并预填字段。
- AI 语义解析结果在编辑器中可见、可覆盖、可提交审核。
- 总览表展示效果列，支持空数据和加载失败。
- 旧 learning-review 入口继续兼容跳转，但不再暗示只有规则回流。

### 集成

- 从校对确认项到规则发布的端到端路径。
- 从校对确认项到知识审核通过的端到端路径。
- 从编辑治理命中到规则或知识候选的路径。
- 发布后的规则命中和知识检索能够反映到对应总览效果列。

## 迁移策略

- 保持现有 learning candidate、review item、learning writeback 数据结构兼容。
- 优先补齐前端入口和候选预填映射，而不是新增中心页。
- 对历史 `knowledge_candidate` 提供列表入口或迁移脚本，避免已有候选无法处理。
- 规则指标优先复用现有规则激活指标表。
- 知识指标可以先通过查询 `knowledge_hit_logs` 聚合，后续再物化为独立指标表。

## 验收标准

- 用户在校对、编辑或筛稿结果中选择 `转规则` 后，可以在规则中心打开该候选，修改完整字段，生成规则草稿，并按现有发布流程发布为可运行规则。
- 用户选择 `转知识` 后，可以在知识库打开该候选，修改完整字段，提交知识审核，并在审核通过后成为可检索知识。
- 候选写回和最终发布状态可追溯，不把草稿误显示为已生效。
- 规则中心总览表显示规则效果列，知识库总览表显示知识效果列。
- 效果列来自日志或指标读模型，不改变核心规则和知识定义。
- AI 语义解析参与预填和审核辅助，但不能绕过人工确认。

## 决策记录

- 不新增全局回流中心。原因是用户不需要看总队列，新增中心会增加导航、权限和状态同步复杂度。
- 效果回看放在规则中心总览和知识库总览。原因是日常运营应靠近资产管理入口，Harness 只作为深度验证和证据来源。
- 候选预填必须复用完整编辑器。原因是简化表单会导致适用范围、证据、AI 语义层和发布治理字段缺失。
- 指标采用派生读模型。原因是运行统计变化频繁，不属于规则或知识定义本身。
